# 출시 점검 리스트 (예시) — 하나라도 [ ] 면 내보내지 않는다

PR 관문(CI · 리뷰 · 머지)을 넘은 뒤, **출시 후보**를 내보내기 전에 QA 가 채웁니다. 팀에 맞게 고쳐 쓰세요.
판정과 서명은 사람(QA)이 합니다. AI 는 테스트 케이스 초안 · 자동/수동 분류 · 실패 분류 근거 · 결과 요약을 돕습니다.

## 0. 대상
- 출시 후보: `<버전 · 커밋 · 빌드 번호>`
- 명세: `specs/<기능>.md` — AC 목록이 이 점검의 기준
- 담당: QA `<이름>` · 개발 `<이름>` · 출시 결정 `<이름>`

## 1. 명세
- [ ] 명세(기획서 Description 포함)의 **[확인 필요] 0건** — 남아 있으면 출시가 아니라 질문부터
- [ ] AC 마다 기대값이 숫자 · 글자로 정해져 있다 (금액은 몇 원 단위로 자르는지까지)

## 2. 테스트 케이스
- [ ] AC 하나에 테스트 케이스 하나 이상 — 자동(단위 · API · 화면 E2E) / 수동으로 나눴다
- [ ] **P0 · P1 테스트 케이스 전부 통과** (수동 포함)
- [ ] 금액 · 정산 · 권한처럼 틀리면 아픈 것은 정답표와 한 줄씩 대조했다

## 3. 자동 검증
- [ ] 단위 · API · E2E 전부 초록 — 빨간불이 있었다면 **분류가 끝났다** (화면 변경 / 제품 버그 / 불안정 / 환경)
- [ ] 제품 버그로 분류된 것은 고쳐졌고, 고친 뒤 다시 돌렸다
- [ ] 테스트 파일을 바꾼 PR 은 따로 승인을 받았다 (기대값을 낮춰 통과시키지 않았다)
- [ ] 검증 장치가 실제로 돌았다 — 결과 파일 · 리포트가 있다 (초록인데 '안 돈' 것이 아닌지)

## 4. 호환 · 비기능
- [ ] (앱) 옛 앱 버전으로 서버 API E2E — 앱은 되돌릴 수 없다
- [ ] (앱) 화면 id 계약을 지웠거나 바꾼 PR 이 없다
- [ ] 성능 · 보안 · 접근성 점검 (팀 기준)

## 5. 내보내기
- [ ] 단계적 출시 계획 (내부 트랙 → 일부 → 전체) · 멈출 기준 (크래시율 · 오류율)
- [ ] 롤백 방법과 담당자 · 연락 경로
- [ ] **Go / No-Go**: QA `[ ] Go  [ ] No-Go` · 이유 한 줄

No-Go 면: 버그 티켓 → 고침 → 이 점검 리스트를 처음부터 다시.
